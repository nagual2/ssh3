# Тест-план R3: быстродействие SSH2 (OpenSSH) vs SSH3 (форк nagual2)

Создан: 2026-09-28. Относится к [ROADMAP.md](ROADMAP.md) §R3. Базовая точка — замер из
[CTO_TASK.md](../CTO_TASK.md) §2: 512 MiB, WSL → Atom x5-Z8350, SSH3 push ≈28.5 / pull ≈24 MB/s
против scp ≈42.5 MB/s (одиночный QUIC-стрим, userspace-крипто без AES-NI, USB btrfs — вероятно,
упирался в диск; настоящая методика исключает диск через tmpfs).

## 1. Цели

1. Воспроизводимые цифры для статьи (R1) и README — с зафиксированным окружением.
2. Локализовать узкие места SSH3: userspace-крипто, одиночный QUIC-стрим, handshake.
3. Показать, где QUIC выигрывает (потери/задержки сети), а не только проигрывает в LAN.

## 2. Метрики

| M | Метрика | Способ измерения |
|---|---------|------------------|
| M1 | Bulk-throughput push/pull, MB/s (k=1 стрим) | 512 MiB random, время стенными часами, sha256-верификация |
| M2 | Суммарный throughput при k=2/4/8 параллельных передачах | k конкурентных процессов, сумма полезных байт / время |
| M3 | Handshake: полный цикл connect+auth+exec (`host true`) | N=30 прогонов, min/median/p95 |
| M4 | Интерактивная задержка: PTY echo RTT | 100 итераций «отправил строку — дождался эха», p50/p95 |
| M5 | Ресурсы сервера при M1: CPU%, peak RSS | сэмплер по `/proc/<pid>/stat` (или pidstat, если есть sysstat) |
| M6 | Устойчивость к качеству сети: throughput + выживание сессии | `tc netem`: 2% loss и 50 ms RTT, по отдельности |

## 3. Стенды

| S | Клиент → Сервер | Путь | Смысл |
|---|-----------------|------|-------|
| S1 | WSL → WSL (loopback, 127.0.0.1) | локально | изоляция цены крипто/CPU: сеть исключена |
| S2 | WSL → minisforum | LAN | Atom x5-Z8350 без AES-NI — CPU-bound worst case; повтор условий замера CTO_TASK |
| S3 | S2 + `tc netem` | LAN с искажениями | M6: сравнение на потерях/задержке |

Оба стенда уже живут с ssh3-server (systemd-юниты). На время тестов деплоится **текущий**
бинарь из репо (v0.1.12, `CGO_ENABLED=0`, тег `disable_password_auth`); прежний бинарь
сохраняется рядом, откат — вернуть файл + `systemctl restart ssh3-server` (правило
test-lifetime:rollback зафиксировать в EchoVault перед постановкой).

## 4. Правила честного сравнения (fairness)

| № | Правило |
|---|---------|
| 1 | Одинаковый механизм передачи у обоих: stdin-пайп `cat > out` (scp — только справочная строка для SSH2, в сравнение не идёт; у SSH3 нормальной передачи ещё нет — Stage 2) |
| 2 | Данные: один файл 512 MiB из `/dev/urandom`, sha256 зафиксирован заранее; источник и приёмник — **tmpfs** (`/dev/shm`), диск исключён |
| 3 | Целостность: sha256 приёмника == эталон, иначе прогон бракуется (заодно страхует от бага Stage 1 №3 — тихая обрезка с rc=0) |
| 4 | SSH2: ключи + `BatchMode`, шифр зафиксирован `-c aes128-gcm@openssh.com`, Compression off; SSH3: pubkey JWT-подпись, тот же ключ ed25519 |
| 5 | Прогрев: первый прогон точки — в корзину; N=10 валидных прогонов на точку; отчёт median + min/max |
| 6 | Чередование ABBA (ssh2,ssh3,ssh3,ssh2…), пауза 2 с между прогонами — чтобы троттлинг Atom не рисовал фиктивное преимущество |
| 7 | Окружение фиксируется в `env.txt` каждого стенда: `ssh -V`, `ssh3 version`, ядро, `/proc/cpuinfo` flags (AES-NI), MTU, governor, load avg |
| 8 | Замеры при пустом хосте; фоновая активность (браузер, билды) запрещена |

## 5. Сценарии

Пользовательский слой (формулировка Пилота, 2026-09-28): **(1) перекачка одного большого
файла, (2) перекачка множества мелких файлов, (3) куча команд в одной сессии**. Метрическая
матрица ниже остаётся как база; сценарии 2 и 3 добавляют B8/B9.

| ID | Метрика | Стенды | Гипотеза |
|----|---------|--------|----------|
| B1 | M1 push k=1 | S1, S2 | на Atom SSH3 отстаёт от SSH2 (userspace-крипто); на loopback разрыв меньше |
| B2 | M1 pull k=1 | S1, S2 | асимметрия push/pull как в замере CTO_TASK |
| B3 | M2 k=2/4/8 | S2 | при k>1 SSH3 подтягивается: узкое место — CPU одного стрима, не транспорт |
| B4 | M3 handshake | S1, S2 | QUIC 1-RTT сопоставим или быстрее TCP+SSH-аутентификации |
| B5 | M4 PTY RTT | S2 | сопоставимо; вклад QUIC-потерь на S3 |
| B6 | M5 CPU/RSS | попутно с B1/B2 | CPU сервера — главный лимитер на Atom |
| B7 | M6 netem 2% loss / 50 ms | S3 | SSH3 деградирует мягче TCP на потерях (главный плюс QUIC) |
| B8 | Многие мелкие файлы | S1, S2 | (а) tar-поток 1000 мелких файлов через пайп — паритетный механизм; (б) справочно: 100 файлов по отдельности `ssh3 -f` против `scp` — цена per-file/per-session overhead |
| B9 | Куча команд в одной сессии | S1, S2 | SSH2: ControlMaster (1 соединение, N exec). SSH3: (а) N процессов клиента — каждый exec = новый коннект (сегодняшний CLI); (б) Go-драйвер поверх `Client.OpenChannel` — N сессий в одном QUIC-коннекте (демонстрация мультиплексинга для статьи) |

Осуществимость B9 проверена по коду: `Client.OpenChannel("session", …)` в библиотеке есть,
в CLI мультиплексирования нет (1 процесс = 1 сессия = 1 соединение); ControlMaster у SSH2 —
родной.

## 6. Скрипты (создать в репо `project/ssh3/bench/`)

| Файл | Назначение |
|------|------------|
| `bench/genfile.sh` | 512 MiB random в `/dev/shm` + эталонный sha256; идемпотентный |
| `bench/genmanyfiles.sh` | (B8) дерево мелких файлов в `/dev/shm`: 1000×4 KiB + 100×100 KiB, tar-эталон + sha манифест |
| `bench/manyfiles.sh` | (B8) tar-поток через пайп (паритет) + пофайловый scp/`ssh3 -f` (справочно) |
| `bench/multidriver/` | (B9б) мини-драйвер на Go: N exec-сессий в одном QUIC-коннекте (Client.OpenChannel) |
| `bench/throughput.sh` | B1–B3: аргументы `transport=ssh2\|ssh3 dir=push\|pull k=N runs=N`; stdout — CSV-строка |
| `bench/handshake.sh` | B4: N прогонов `… true`, min/median/p95 (hyperfine, при отсутствии — bash-цикл) |
| `bench/pty_rtt.py` | B5: python3+pexpect, 100 echo-итераций, p50/p95 (фолбэк без pexpect — expect/родной питон-pty) |
| `bench/cpu_sample.sh` | B6: сэмплер CPU%/RSS процесса ssh3-server/sshd во время передачи |

Зависимости WSL: `hyperfine`, `sysstat`, `python3-pexpect` — опциональны, у каждого скрипта
есть фолбэк; ставить только недостающее и только по согласованию.

## 8. Критерии готовности

1. Каждая точка B1–B5 имеет ≥10 валидных прогонов, все sha256 сошлись.
2. `env.txt` для S1–S3 приложен к отчёту.
3. Отчёт в `docs/` с таблицами и выводами; цифры готовы к цитированию в R1.
4. Стенды возвращены в исходное состояние (нет netem-правил, прежние бинари).

Статус реализации (2026-09-28, вечер): комплект `bench/` готов и проверен смоуками на S1
(genfile, handshake 3/3, push 80.6/43.1 MB/s, pull 58.6 MB/s c CR-воркараундом, pty_rtt
p50≈0.1 мс, cpu_sample локально и удалённо). Матрица не запускалась: хост занят параллельной
сборкой билда — на нагрузке pull-прогоны отбраковываются по sha (см. §9.8).

## 9. Риски и ловушки

| № | Риск | Обход |
|---|------|-------|
| 1 | Диск как бутылочное горлышко (как в замере CTO_TASK: USB btrfs) | tmpfs на обоих концах |
| 2 | AES-NI: SSH2 aes-gcm через DI-инструкции x86 vs userspace Go-крипто — на Atom это главный фактор; сравнение честное, но выводы формулировать с оговоркой про CPU | отдельно подсветить в отчёте; loopback S1 отделяет крипто от сети |
| 3 | PMTU/MTU в WSL NAT ломает QUIC-оптимумы | зафиксировать MTU в env.txt, не менять в ходе прогона |
| 4 | `tc netem` на общем интерфейсе режет весь трафик хоста | применять точечно и на короткое время, откат немедленно после B7 |
| 5 | Троттлинг Atom искажает серию | чередование ABBA, паузы, фиксация governor |
| 6 | Отсутствие hyperfine/pexpect/sysstat | фолбэки в скриптах (bash-таймер, python-pty, /proc-сэмплер); hyperfine из плана исключён |
| 7 | ~~Клиентский баг форка: одиночный `\r` в конце stdout exec-сессии~~ **исправлен в v0.1.14** (коммит `72bec27`: `defer Printf("\r")` обёрнут в `if ptyRequested`) | воркараунды в bench (`remote_sha` чистит `\r`, pull срезает хвостовой CR) оставлены как регрессионная страховка — на чистом клиенте не срабатывают |
| 8 | Pull обрывается при загрузке хоста (параллельные сборки) — отбраковка по sha срабатывает как задумано | матрицу гонять на холостом хосте; retry-логика прогоняет до 2N попыток |

## Отклонения от первоначального плана (по ходу реализации)

1. hyperfine не используется — равномерный bash-таймер `date +%s%N` (детерминированно, без зависимостей).
2. Добавлен справочный сценарий `--mech file`: `ssh3 -f` против `scp` (push only), паритетный baseline остаётся stdin-пайпом. Нюанс: `-f` пишет в домашний каталог сервера (диск, не tmpfs) — цифры сравнивать с оговоркой; у `-f` есть встроенная checksum-верификация.
3. `pty_rtt.py` принимает клиентскую команду через `--client-cmd` или env `CLIENT_CMD`, pexpect не нужен (stdlib `pty`).
4. `run_all.sh --transports ssh2,ssh3` — прогон по подмножеству транспортов (S1 без sshd не блокирует весь стенд).
5. Пользовательские сценарии реализованы: B8 — `genmanyfiles.sh` (1000×4 KiB + 100×100 KiB, манифест sha256) + `manyfiles.sh` (tar-поток — паритет; per-file `ssh3 -f` vs `scp` — справочно); B9 — `batchexec.sh` (ssh2cold / ssh2cm с настоящим ControlMaster / ssh3cli). B9(б) multidriver на Go — после mux-кодека Stage 3.5.
6. **Баг форка №6**: `ssh3 -f` отказывается работать с абсолютным удалённым путём («file does not exist» даже в существующем каталоге); работает только HOME-относительный путь. В bench все `-f`-сценарии используют относительный `ssh3-bench-file/` / `ssh3-bench-manyfiles/`; `-f` не создаёт удалённые каталоги — mkdir делается явно. Кандидат в Stage 1 CTO_TASK.
