# Профиль data-path SSH3 (Stage 1.5, инкремент 1)

Дата: 2026-09-29, v0.1.15+pprof-хуки, S1 loopback, push 1 GiB, ~116 MB/s во время съёма.

## Решающий замер: потолок транспорта

| Замер | MB/s |
|-------|------|
| Голый vendored quic-go v0.40.1, 1 стрим, loopback (`internal/interop/quic_bench`) | **326** |
| SSH3 клиент→сервер тот же объём | 130 |
| OpenSSH (SSH2) тот же объём | 365–488 |

Вывод: транспорт не является потолком (326 > 130), но и SSH2 недотягивает —
основные резервы: слой ssh3 (−200 MB/s) и тюнинг/апгрейд quic-go (+сверх 326).

## CPU-профили во время передачи (pprof, окно 7 c)

| Позиция | Клиент | Сервер |
|---------|--------|--------|
| `runtime/internal/syscall.Syscall6` (UDP I/O) | **39.1%** | **25.1%** |
| `runtime.memmove` | 5.0% | 6.5% |
| `runtime.futex` | 5.3% | 3.4% |
| GC (scanobject/findObject/memclr/…) | ~7% | ~10% |
| `crypto/aes.gcmAesEnc/Dec` | **2.9%** | **2.3–2.5%** |
| ssh3-слой (message/channel) | вне top-12 | вне top-12 |

## Вердикт

1. **Системные вызовы — главный убийца** (39% клиента, 25% сервера): пакетный
   UDP I/O без эффективного батчинга. GSO (UDP_SEGMENT) в v0.40.1 либо не
   активируется, либо не даёт эффекта в этой конфигурации — проверить и включить
   (инкремент 2), либо получить его апгрейдом quic-go (инкремент 3).
2. **AES невиновен**: ~3% CPU на каждой стороне — AES-NI отрабатывает как надо.
3. **Слой ssh3** — вне top-12; его вклад вторичен по отношению к syscall-шторму.
4. GC/аллокации ~7–15% — переиспользование буферов даст умеренный процент.

Дорожка: инкремент 2 — GSO/датаграммы/окна; инкремент 3 — апгрейд quic-go
(пере-базировка vendor/h3 shim); инкремент 4 — фиксы слоя по профилю.

## Инкремент 2: GSO A/B и бисекция сокета (2026-09-29)

| Эксперимент (quic_bench, 256 MiB, loopback) | MB/s |
|---------------------------------------------|------|
| GSO on (умолчание quic-go) | **294.8** |
| `QUIC_GO_DISABLE_GSO=true` | **94.1** |
| `quic.DialAddr` (direct) | 274.5 |
| ssh3-стиль: dual-stack `net.ListenUDP("udp")` + `quic.Dial` | 257–271 |
| полный ssh3 (клиент+сервер, h3+каналы) | 130 |

Выводы:

1. GSO даёт **×3.1** (94 → 295): батчинг sendto — главный рычаг. У SSH2 он «бесплатно»
   есть в ядре (GSO/GRO на TCP), у QUIC он обязан делать сам.
2. Стиль создания сокета (dual-stack, pre-created conn) **не влияет** — полный ssh3 теряет
   не там.
3. Кумулятивный профиль клиента: `sendQueue.Run → sconn/oobConn.WritePacket` = **33% cum** —
   в ssh3-пути батчинг фактически не работает (иначе syscall-доля была бы единицами
   процентов); наш stdin-памп + `WriteData` = ~14% cum.
4. `channel.MaxPacketSize = 30000` — сообщения канала 30 KiB, нарезка не мусор; потери
   размазаны по h3-фреймингу, копиям и send-очереди quic-go.

След: самый тяжёлый рычаг — инкремент 3 (апгрейд quic-go: в свежих версиях send-очередь и
GSO-путь переписаны, баги «disable-on-error» починены), затем инкремент 4 (слой).

## Свежий профиль v0.1.20 (quic-go v0.63) и инкремент 4: пул буферов сервера (2026-09-30)

Стенд S1 loopback, SSH3_PPROF, 512–1024 MiB, тихая машина.

| Профиль | Top |
|---------|-----|
| Сервер, pull (отдача) | `Syscall6` 35% (send+ACK-recv), futex 5.5%, memmove 3.4%, gcmAesEnc 2.7%, GC ~7% cum, `selectgo` ~3% |
| Клиент, push (отдача) | `Syscall6` **43%** — по составу это приём ACK-датаграмм; `packetPacker.appendPacket` 23% cum, `runtime.schedule` 13% cum, `selectgo` 4%, `growslice` 3.8% |

Выводы: (1) GSO в v0.63 работает — `QUIC_GO_DISABLE_GSO=1` роняет push на −34%
(157→104 МБ/с); вывод «GSO не работает в полном пути» из замеров v0.40.1 устарел.
(2) Слой ssh3 теперь дороже send-сисколлов: полный стек (~157–175 МБ/с) ниже raw-plain
потолка UDP (~241 МБ/с, `temp/ssh3-nginx-method/`); главный остаток — goroutine-модель
и per-packet обработка QUIC (ACK-шторм на приёме), т.е. quic-go-территория.

Инкремент 4a (этот): `cmd/ssh3-server.go` readStdout/readStderr — было 2 аллокации +
копия + hop на каждый чанк; стало `sync.Pool` буферов `MaxPacketSize`, владение
передаётся через `readResult.raw`, потребитель возвращает буфер после `WriteData`.
A/B (256 MiB, ABBA, один и тот же клиент, серверы base/opt на :4433): pull медиана
**159.9 → 172.3 МБ/с (+7.8%)**, диапазоны почти непересекающиеся; push-контроль без
регресса. `go test -tags disable_password_auth ./...` — все зелёные, sha-верификация
каждого pull-прогона пройдена.

След (инкремент 4b): приём ACK (quic-go), сокращение goroutine-хопов (`schedule`+`selectgo`
~17% cum на клиенте), `growslice` в packetPacker — следующая сессия по свежему профилю.
